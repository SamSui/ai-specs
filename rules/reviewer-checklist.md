# Reviewer 快速检查清单

> **定位**：基于 `review-rules.md` 23条原则的浓缩版快速检查表，供评审时快速对照。  
> **适用对象**：Reviewer Agent、人工代码评审者。

---

## 证据基础（R-01 ~ R-03）

- [ ] **R-01**: 是否读取了原始文件，而非仅依赖 grep/ls/wc 等工具输出？
- [ ] **R-02**: 每条结论是否附带了文件路径 + 行号或命令输出？
- [ ] **R-03**: 是否区分了"文档描述"与"实际实现"，并分别核实？

## 方法基础（R-04 ~ R-06）

- [ ] **R-04**: 测试中 assumeTrue 是否被正确识别为"未验证"而非"通过"？
- [ ] **R-05**: 是否逐章节精读，而非仅用 grep 扫描关键词？
- [ ] **R-06**: 是否对照了至少 2 个文档进行交叉验证？

## 关键判定（R-07 ~ R-09）

- [ ] **R-07**: BUILD SUCCESS 是否被质疑——Maven 绕过了什么？
- [ ] **R-08**: 性能结论是否基于真实数据 + 真实 I/O，而非 synthetic data？
- [ ] **R-09**: 遇到评审障碍时是否 STOP 并上报，而非绕过？

## 矛盾识别（R-10 ~ R-13）

- [ ] **R-10**: 发现的矛盾是否全部报告，未选择性忽略？
- [ ] **R-11**: 单位是否一致（MB/MiB、ms/s 等）？
- [ ] **R-12**: 需求编号是否在对齐的文档间保持一致？
- [ ] **R-13**: 范围边界是否清晰，有无模糊风险？

## 缺口判定（R-14 ~ R-18）

- [ ] **R-14**: 不存在的文件/测试是否标记为 ❌，而非"待补充"？
- [ ] **R-15**: 🟡 状态是否在 checkpoint 后明确转为 ✅/❌？
- [ ] **R-16**: 缺口是否用精确数字描述（覆盖率精确到个位）？
- [ ] **R-17**: 未核实的内容是否标记为 ❌，而非时间不够就写 ✅？
- [ ] **R-18**: 上轮发现的 ❌ 问题是否在本轮继续跟踪直至关闭？

## 态度约束（R-19 ~ R-23）

- [ ] **R-19**: ⚠️/Done 标记是否精确使用，无模糊状态？
- [ ] **R-20**: 每个"通过/完成"结论是否先验证了证据充分性？
- [ ] **R-21**: 不确定的内容是否明确标注"未核实"？
- [ ] **R-22**: 是否同时正向找证据 + 反向找反例？
- [ ] **R-23**: 本次评审的方法论本身是否被反思（Completion Bias 自检）？

---

## 7 维度快速检查

| 维度 | 检查要点 | 结论 |
|------|----------|------|
| 功能正确性 | 功能完整？边界条件处理？逻辑错误？ | ✅/⚠️/❌ |
| 代码质量 | 风格一致？DRY？函数<50行？无硬编码？ | ✅/⚠️/❌ |
| 安全审查 | 无注入风险？敏感信息不暴露？ | ✅/⚠️/❌ |
| 性能检查 | 无 N+1？无冗余循环？单位一致？ | ✅/⚠️/❌ |
| 架构设计 | 模块清晰？无循环依赖？扩展性？ | ✅/⚠️/❌ |
| 测试覆盖 | 核心逻辑覆盖？边界覆盖？防回归？ | ✅/⚠️/❌ |
| 文档完整性 | 关键注释？API 文档？README？ | ✅/⚠️/❌ |

---

## Handoff 前自检

- [ ] 7 维度全部检查且结论明确
- [ ] P0/P1/P2 问题分类清晰
- [ ] Evidence 包含文件 + 行号，标注一手/二手来源
- [ ] 矛盾报告章节存在（C-001 起或"无矛盾"）
- [ ] 编号映射表存在（或"无需映射"）
- [ ] 最终结论三选一：✅通过 / 🟡有条件通过 / ❌不通过
