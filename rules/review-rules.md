## 1. 总则

### 1.1 目的

本规范定义 AI Wisdom Governance 项目评审的分析方法论，确保评审过程：

- 基于可回溯的一手证据，而非摘要/二手结论
- 通过跨文档对比发现矛盾，而非单文档扫描
- 明确区分未核实与已完成，不模糊状态
- 主动识别缺口，而非只找符合项
- 保持元认知警觉，不因 Completion Bias 而降低标准

### 1.2 评审核心原则

> **"文档描述 ≠ 实际实现"**  
> README/memory/摘要 说的，和源码 实的，是两回事。必须分开核实。

### 1.3 优先级框架

评审规则按以下依赖层级排序：

```
第一层（证据基础）
  └─ 工具输出是二手结论
  └─ 证据必须有回溯路径
  └─ 文档描述 ≠ 实际实现

第二层（方法基础）
  └─ assumeTrue = 跳过 = 未验证
  └─ 逐章节精读 > grep 扫描
  └─ 跨文档对比才能发现矛盾

第三层（关键判定）
  └─ BUILD SUCCESS 不代表代码无错
  └─ 架构验证 ≠ 性能实测
  └─ 评审障碍 → STOP，不绕过

第四层（矛盾识别）
  └─ 矛盾不能跳过
  └─ 单位不一致是矛盾
  └─ 需求编号不一致要报告
  └─ 范围边界模糊是风险

第五层（缺口判定）
  └─ 空白 ≠ 合格
  └─ 🟡 = 未核实 = checkpoint 后 ❌
  └─ 缺口必须有数字
  └─ 没核实 = ❌
  └─ 未解决问题必须持续跟踪

第六层（态度约束）
  └─ ⚠️/Done 标记掩盖问题
  └─ 掂量自己说的内容
  └─ 承认不知道
  └─ 正向找证据 + 反向找反例
  └─ 掂量自己的方法论
  └─ 掂量掂量掂量这件事本身
```

---

## 2. 评审约束（23条）

### 第一层：证据基础

**R-01：工具输出是二手结论**
❌ 禁止：grep/wc/ls/Maven 输出当一手证据；只写"经过核实"无路径附注
✅ 必须：读原始文件；摘要/报告二手结论必须验证；区分文档说/代码实/测试跑三手

**R-02：证据必须有回溯路径**
❌ 禁止：只写"经过核实"无路径附注；用"写了自己核实"糊弄自己
✅ 必须：每条结论附"文件+行号"或"命令输出"；掂量方法论本身有没有 Completion Bias

**R-03：文档描述 ≠ 实际实现**
❌ 禁止：README/memory/摘要 说的，和源码 实的，混在一起当结论
✅ 必须：分开核实，写明"文档描述X，源码实现Y"

---

### 第二层：方法基础

**R-04：assumeTrue = 跳过 = 未验证**
❌ 禁止：assumeTrue 计为"部分通过"；@Test 总数当测试覆盖
✅ 必须：@Test/assumeTrue/assert 分别计数；assumeTrue → 未跑 → 未验证

**R-05：逐章节精读 > grep 扫描**
❌ 禁止：grep 匹配关键词当矛盾检测；grep 匹配不到就当不存在
✅ 必须：逐章节读，建立语义关联；同义词/不同描述/不同单位，grep 都抓不到

**R-06：跨文档对比才能发现矛盾**
❌ 禁止：单文档内扫描当矛盾检测
✅ 必须：至少两文档对照；同义/同值不同描述 → 矛盾

---

### 第三层：关键判定

**R-07：BUILD SUCCESS 不代表代码无错**
❌ 禁止：Maven BUILD SUCCESS = 编译通过
✅ 必须：问"Maven 绕过了什么"；记录 javac vs Maven 的差异

**R-08：架构验证 ≠ 性能实测**
❌ 禁止：synthetic data 架构验证当实测性能
✅ 必须：真实数据 + 真实文件 I/O + 实测指标

**R-09：评审障碍 → STOP，不绕过**
❌ 禁止：工具失败/API 错误/路径不存在 → workaround 继续
✅ 必须：立即 BLOCK；"Not in list" ≠ 绕过许可

---

### 第四层：矛盾识别

**R-10：矛盾不能跳过**
❌ 禁止：选一个"似乎合理"的版本忽略其他
✅ 必须：矛盾必须报告；不能选择不能忽略

**R-11：单位不一致是矛盾**
❌ 禁止：混用 MB/MiB、GB/GiB、ms/s
✅ 必须：区分物理意义；5GB = 5×1000³ 还是 5×1024³，结论不同

**R-12：需求编号不一致要报告**
❌ 禁止：忽略 acceptance-criteria 和 requirements-spec 编号体系不同
✅ 必须：映射并报告；编号不一致反映深层问题

**R-13：范围边界模糊是风险**
❌ 禁止：In Scope 和 Out of Scope 都无明确时，跳过
✅ 必须：标注"边界模糊"；决策前先澄清

---

### 第五层：缺口判定

**R-14：空白 ≠ 合格**
❌ 禁止：测试文件不存在 → "待补充" → 当✅
✅ 必须：文件不存在 → ❌

**R-15：🟡 = 未核实 = checkpoint 后 ❌**
❌ 禁止：checkpoint 时间到仍留🟡
✅ 必须：🟡 只表示进行中；时间节点后 → 明确✅/❌

**R-16：缺口必须有数字**
❌ 禁止：基本完成/大部分/似乎
✅ 必须：缺口数/覆盖率/跳过率 → 精确到个位；每条 AC 判定可量化/不可量化

**R-17：没核实 = ❌**
❌ 禁止：时间不够 → 写✅
✅ 必须：没核实的内容 → ❌；掂量"时间不够"是不是借口

**R-18：未解决问题必须持续跟踪**
❌ 禁止：发现但来不及 → 下次报告消失
✅ 必须：每个❌ 在下次报告继续出现，直至关闭

---

### 第六层：态度约束

**R-19：⚠️/Done 标记掩盖问题**
❌ 禁止：⚠️当中间状态保留；Done 当完成结论
✅ 必须：⚠️=未完成；Done=完成；未核实=❌，三选一不能模糊

**R-20：掂量自己说的内容**
❌ 禁止：memory/摘要里写"通过/完成"，不核实水分
✅ 必须：每个"通过/完成"先过一遍"证据足不足"

**R-21：承认不知道**
❌ 禁止：没十足把握 → 模糊带过
✅ 必须：写"未核实"；假装知道比承认不知道更危险

**R-22：正向找证据 + 反向找反例**
❌ 禁止：只找"符合 spec 的证据"
✅ 必须：主动找"不符合 spec 的反例"

**R-23：掂量自己的方法论**
❌ 禁止：认为"这 次列了不剪枝"就默认真的不剪枝；认为"已经反思过了"就默认反思到位了
✅ 必须：我本身也有 Completion Bias；不能因为这 次说了"反思"就默认反思彻底了

---

## 3. 使用说明

### 3.1 评审执行顺序

每次评审按 R-01 → R-23 顺序执行，上层未通过不得进入下层。

### 3.2 违反判定

- 违反 R-01~R-09（第一至第三层）→ 🔴 严重，必须修复
- 违反 R-10~R-13（第四层） → 🟠 中等，必须报告
- 违反 R-14~R-18（第五层） → 🟡 需确认，有正当理由可接受
- 违反 R-19~R-23（第六层） → ⚠️ 需记录，评审者自检

每条约束均来自 [项目名称] 评审实践中的真实教训，详见记忆文件 `memory/2026-04-05.md`。
