# Interview Skill — 决策采访技能

## 何时使用

满足以下任一条件时，触发本技能：
1. Owner 说"逐项采访我"、"逐条采访"、"一个个确认"
2. 需要 Owner 做决策，且有 ≥1 个可选方案
3. 架构师向 Owner 征询技术/产品/资源决策
4. **Owner 说"分步确认"或"多 TAB"** → 使用多 TAB 提问模式

**不适用于**：纯信息查询、状态汇报、无需决策的进度同步。

---

## 核心流程

```
1. 【收集】把待决策问题整理成结构化选项
2. 【判断模式】
   ├── 问题数 ≥2 且用户要求分步/TAB → 使用多 TAB 提问模式
   └── 其他情况 → 使用单题提问模式
3. 【提问】使用 AskUserQuestion 工具向用户发出问题
4. 【等待】用户选择选项（A/B/C）或切换 TAB 答题
5. 【记录】每个决策结果 → 记录到 AGENTS.md / 更新 ADR
```

---

## 提问格式要求（每个问题必须包含）

每个提问必须包含以下 7 个要素，缺一不可：

| # | 要素 | 说明 |
|---|------|------|
| 1 | **问题** | 要决策的具体事项（简洁一句话） |
| 2 | **背景** | 为什么这个问题需要现在决策，对项目有何影响 |
| 3 | **原因** | 为什么现在需要做这个决策（时机、约束、风险） |
| 4 | **建议** | 我的推荐选项及理由 |
| 5 | **0号文档对应** | 引用 `document/specs/00-智能治理——数据预处理.md` 的具体章节 |
| 6 | **交付验收** | `必须` — 0号文档交付验收必须项 / `可选` — 非必须，可跳过 |
| 7 | **过度设计** | `是` — 当前需求超出0号文档范围 / `否` — 符合0号文档范围 |

## 提问模式

### 模式一：单题提问（默认）

每次只提一个问题，用户回答后再提下一个。

```
AskUserQuestion 问题数组: [{question_1}]
用户回答 Q1 → AskUserQuestion 问题数组: [{question_2}]
用户回答 Q2 → ...
```

### 模式二：多 TAB 提问

一次展示多个 TAB，每个 TAB 一个问题，用户可以切换 TAB 顺序答题。

```
┌─────────┬─────────┬─────────┬─────────┐
│ 步骤1/4 │ 步骤2/4 │ 步骤3/4 │ 步骤4/4 │  ← 用户可切换 TAB
│  Q1内容 │  Q2内容 │  Q3内容 │  Q4内容 │
│[下一步] │[上一步] │[上一步] │[上一步] │
│         │[下一步] │[下一步] │[完成]   │
└─────────┴─────────┴─────────┴─────────┘
```

**触发条件**：
- 用户明确说"分步"、"多 TAB"、"分几页"
- 问题数 ≥2 且为独立步骤类问题

## AskUserQuestion 格式规范

### 单题模式参数

| 字段 | 来源 | 约束 |
|------|------|------|
| `header` | `{分类标签} Q{序号}` | 最多 12 字符 |
| `question` | **问题/背景/原因/建议/0号文档对应/交付验收/过度设计** 的完整描述 | 必须包含七要素 |
| `options` | 每个选项含 `label` 和 `description` | 2~4 个选项 |
| `multi_select` | `false`（默认单选） | 除非用户要求多选 |

### 多 TAB 模式参数

| 字段 | 来源 | 约束 |
|------|------|------|
| `header` | `{任务描述} {序号}/{总数}`（如 `步骤1/4`） | 格式： `{x}/{n}` |
| `question` | 当前步骤的具体问题或操作描述 | 一题一问 |
| `options` | 导航选项 + 答题选项 | 首尾 TAB 有导航 |
| `multi_select` | `false` | 除非用户要求多选 |

### question 文本模板

**单题模式（七要素完整版）**：
```markdown
**问题**: {要决策的具体事项}

**背景**: {为什么这个问题需要现在决策，对项目有何影响}

**原因**: {为什么现在需要做这个决策（时机、约束、风险）}

**建议**: {我的推荐选项及理由}

**0号文档对应**: {引用 0号文档 的具体章节和需求描述}
- 章节：{标题}
- 需求：{相关描述}

**交付验收**: {必须 / 可选}

**过度设计**: {是 / 否 — 当前需求是否超出0号文档范围}
```

**多 TAB 模式（步骤确认版）**：
```markdown
【步骤 {序号}/{总数}】

**问题**: {具体操作描述}

**背景**: {为什么要做这个步骤}

**0号文档对应**: {引用章节}
**交付验收**: {必须/可选}
**过度设计**: {是/否}
```

### 选项设计规范

**单题模式 options**：
- `label`：简洁标识 + 选项字母，如 `"A: API刷新缓存 (Recommended)"`
- `description`：说明**选这个选项后的具体方向和结果**
- 推荐项末尾加 `"(Recommended)"`

**多 TAB 模式 options**：
- 首 TAB：`[{label: "下一步 →", description: "✅ 完成"}, ...]`
- 中间 TAB：`[{label: "← 上一步", description: "返回"}, {label: "下一步 →", description: "✅ 完成"}, ...]`
- 末 TAB：`[{label: "← 上一步", description: "返回"}, {label: "完成", description: "✅ 全部完成！"}, ...]`

> 系统会自动追加 `Other` 选项，用户可输入自定义想法。

## 交互协议

### 用户响应方式

- **单题模式**：点击选项按钮 A/B/C，或在 Other 中输入想法
- **多 TAB 模式**：切换 TAB 点击答题，或直接点击选项

### 多 TAB 模式导航规则

1. **首次进入**：显示第 1 个 TAB
2. **点击"下一步 →"**：自动切换到下一个 TAB
3. **点击"← 上一步"**：返回上一 TAB（用户可修改之前的选择）
4. **末 TAB 点击"完成"**：收集所有答案，输出汇总结果

### 决策结果记录

**单题模式**（每次回答后立即记录）：
```markdown
✅ Q-{序号} 决策：{选项字母 / 自定义摘要}

**问题**: {问题描述}
**决策时间**: {HH:MM}
**落地位置**: {ADR文件名或章节}
```

**多 TAB 模式**（全部完成后汇总）：
```markdown
✅ 分步采访完成（共 N 项）

1. 步骤1/4 决策：{答案}
2. 步骤2/4 决策：{答案}
...

**决策时间**: {HH:MM}
**落地位置**: {ADR文件名或章节}
```

## 0号文档引用规则

### 0号文档定位

每个项目的 0号文档 指代文件不同，从项目记忆或 Agent 记忆中提取：

| 项目 | 0号文档路径 |
|------|-------------|
| aiwg | `document/specs/00-智能治理——数据预处理.md` |
| {其他} | {根据项目 CLAUDE.md 或记忆确定} |

### 引用格式

```markdown
**0号文档对应**:
- 章节：{章节标题}
- 原文摘录：{与本问题相关的 0号文档 内容片段}
- 需求类型：{功能需求 / 性能需求 / 质量要求 / ...}
```

## 常见错误

| # | 错误 | 正确做法 |
|---|------|---------|
| 1 | 提问缺少七要素之一 | 每个问题必须包含：问题/背景/原因/建议/0号文档对应/交付验收/过度设计 |
| 2 | 0号文档引用不具体 | 必须引用具体章节和需求描述，不能只写"见0号文档" |
| 3 | 交付验收标注错误 | 必须明确标注"必须"或"可选"，影响决策优先级 |
| 4 | 过度设计判断缺失 | 必须明确标注"是"或"否"，帮助 Owner 判断是否值得投入 |
| 5 | 多 TAB 模式缺少导航 | 首/中间/末 TAB 必须包含导航选项 |

## 示例对话

### 单题模式示例（数据去重策略）

**架构师**（调用 AskUserQuestion）：
```json
{
  "questions": [{
    "header": "去重策略 Q1",
    "question": "**问题**: 数据集去重策略选择——完全一致 vs 语义相似\n\n**背景**: 当前数据集存在两类重复：完全重复的相同文件，以及内容相似但略有差异的相似文件。需要确定去重的粒度。\n\n**原因**: ETL Pipeline 即将开发，去重策略直接影响数据清洗环节的实现方式。选错策略会导致要么去重不彻底（留冗余），要么误删有效数据。\n\n**建议**: 推荐 `B`（分层去重），理由：\n1. 先行计算哈希，快速剔除完全重复\n2. 再用语义相似度算法处理近似内容\n3. 平衡准确性与性能\n\n**0号文档对应**:\n- 章节：数据清洗与去噪 → 重复内容检测\n- 原文摘录：\"对于文本内容，系统采用多层次的重复检测策略，首先使用哈希算法快速识别完全相同的文本，然后使用文本相似度算法检测语义相近或结构相似的内容。\"\n- 需求类型：功能需求（核心流程）\n\n**交付验收**: 必须\n**过度设计**: 否 — 完全符合0号文档描述的分层策略",
    "options": [
      {"label": "A: 仅完全一致去重", "description": "只去除哈希值完全相同的文件，简单但可能留冗余"},
      {"label": "B: 分层去重 (Recommended)", "description": "哈希去重 + 语义相似度检测，平衡准确与性能"},
      {"label": "C: 全部语义去重", "description": "对所有内容计算语义相似度，准确但性能差"}
    ]
  }]
}
```

**Owner**: 选择 `B`

**架构师**:
> ✅ Q1 决策：B（分层去重）
>
> **问题**: 数据集去重策略选择
> **落地位置**: `document/decisions/ADR-xxx-deduplication.md`

## 与 task-publish 的关系

- **task-publish** 管"任务怎么调度执行"
- **interview** 管"架构师和 Owner 之间的决策闭环"

两者结合：Owner 通过 interview 做决策 → 架构师通过 task-publish 调度执行。
