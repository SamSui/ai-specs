# ADR 正文模板

## 创建判断

创建独立 ADR 前逐项回答：

- 是否影响多个仓库、服务、前端或部署组件？
- 是否改变跨系统数据、接口、权限、命名、生命周期、计费或测试架构？
- 未来开发者是否需要知道“为什么这样做”？
- 是否存在替代方案、取舍或兼容边界？
- 是否需要测试、E2E、部署或跨系统数据证明？

如果只是单行文案、局部样式、普通路由、机械重命名或已有 ADR 覆盖的 FIX，归入主题 README 的偏离/FIX 表；实施证据归入 `result.md` 或 `HANDOVER.md`。

## 推荐模板

```markdown
# ADR-NNN：标题

| 属性 | 值 |
|------|-----|
| 创建日期 | YYYY-MM-DD |
| 归档日期 | YYYY-MM-DD；设计阶段留空 |
| 最后核验日期 | YYYY-MM-DD；未核验则留空 |
| 状态 | proposed / accepted / deprecated / superseded |
| 仓库 | repo-a、repo-b |
| 来源 | 原始需求、问题单、任务前调查或既有文档 |

---

## 1. 背景与用户故事

说明业务目标、触发问题、受影响入口和用户价值。跨系统任务在本节后使用 Mermaid 调用链图标明入口、服务边界、数据形态和展示出口。

## 2. 范围与偏离

列出改造前事实、P0/P1 偏离、受影响仓库和明确不在范围项。多主题输入必须在主题 README 或偏离矩阵保留“输入主题 -> ADR / FIX / 明确排除项”映射。偏离细项、FIX 编号和代码落点放在主题 README 或偏离矩阵；正文只保留支撑决策所需的内容。

## 3. 重大决策

### 决策 1：明确的规则

先写规则，再写理由、适用条件和反例。

### 决策 2：跨系统契约

用列表、公式、状态机、命名格式或调用链写清上下游约束。

## 4. 替代方案与不选原因

- **方案 A** → 优点；缺点；不选原因。
- **方案 B** → 优点；缺点；不选原因。

## 5. 项目认知、后果与触发条件

记录稳定的排查方法、协议边界、技术债务、兼容风险和重新立项条件。可跨会话复用的结论同步至 Beads memory。

## 6. 执行状态

只保留按偏离/FIX 汇总的实施状态与验证状态，以及尚未解决的边界。详细提交、测试输出、CI/CD job、部署过程、E2E 证据和交接入口放入 `result.md` 或 `HANDOVER.md`。

## 7. 关联 ADR

- [[NNN-标题]] → 关系和依赖原因。
```

## 写作要求

- 用任务前视角写背景、偏离、决策、范围和后果；即使文档后补，也不得以“会话归档”“会话任务主线”“本轮过程”等事后叙述组织正文。
- 记录 why、边界和后果，不只记录 what；跨系统背景优先用 Mermaid 图表达链路和字段/文件形态边界。
- 计算、权限、状态机、生命周期、命名和跨仓协议优先用列表、公式或状态图。
- 不修项、技术债务、环境阻塞和失败验证必须保留，但不得把它们伪装为已经完成。
- 执行状态必须分为实现状态和验证状态；“已修复”只能在两种状态均有相应证据时作为组合结论，不能替代两列。
- 创建日期表示最初决策日期，并关联需求、问题单或最早调查来源；归档日期表示文档完成归档日期；最后核验日期表示最新证据日期。状态表中的每条证据必须包含类型、最小可追溯标识和发生日期；归档或核验日期不得早于其引用的提交、测试或环境证据。
- 新增偏离/FIX 而不改变既有决策时更新主题 README 或偏离矩阵；只有决策、适用范围、契约或后果变化时才修订 ADR 正文。
- 引用文件路径和行号时以当前代码核实为准；历史证据仅保留能支撑决策或状态的最小标识，不复制完整命令日志。
- 用户明确的决策写入正文，并按长期价值同步 Beads memory；写入或更新使用 `bd remember`。
- 禁止将 Skill 提取、文档整理、聊天过程、CI/CD job 过程或模板化验收章节写入 ADR 正文。
- 不把凭据、Token、密码、连接串、Cookie、Authorization header 或未脱敏用户数据写入 ADR。
