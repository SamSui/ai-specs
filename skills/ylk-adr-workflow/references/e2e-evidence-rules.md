# E2E 与验证证据规则

## 验证层级

按风险选择并明确写出实际完成的层级：

- **代码核实** → 实现和契约一致。
- **单元测试** → 后端业务分支、空值、边界、保留规则和持久化参数。
- **编译/lint/typecheck/build** → 对应模块真实构建命令和环境。
- **API/DB** → 操作前后字段和跨系统状态核对。
- **UI/E2E** → 真实页面操作、DOM 展示和交互路径。
- **部署回归** → 实际 JAR/镜像、rollout、日志、关键 API 和页面。

验证任务和每轮结果由 Beads issue 跟踪；最终结论写入 ADR、`result.md` 或 `HANDOVER.md`。不要把每轮日志全部复制进 ADR。

## E2E 基本原则

### 登录态检查

连接浏览器后先检查 token/session 是否存在且未过期。401、登录跳转和无权限必须显式记录，不能被空列表或宽松断言掩盖。

### 具体业务断言

测试用例必须验证具体业务数据、字段、状态、金额、路由、文本或跨系统变化。以下断言不足以证明业务正确：

- 只检查 HTTP status 是 200。
- 只检查 `data.total >= 0`。
- 只检查页面没有抛异常。
- 只检查 API 返回对象存在但不核对字段。

### API 与 UI 的关系

API 调用可以验证页面展示值和后端数据，但不能替代真实页面导航、点击、输入、弹窗和 DOM 断言。微前端、Wujie、SPA 使用当前应用实际导航机制；动态路由优先 router 导航。

### 失败证据三件套

每条失败用例至少保留：

1. 截图，能看到失败现场或验证区块。
2. API/网络记录，包含脱敏 URL、请求和响应关键信息。
3. 明确 reason，说明预期、实际、环境和下一步定位方向。

### 跨系统一致性

涉及数据变更时按以下顺序：

1. 记录操作前关键字段。
2. 执行真实 UI 操作。
3. 重新查询 API，核对操作后字段。
4. 必要时只读 DB 绕过缓存。
5. 对比上下游状态、时间、金额、规格、ID 和对象路径。

### 测试夹具

夹具必须记录：

- 修改哪些数据以及为什么。
- 修改前原值。
- 测试后还原命令和顺序。
- 是否需要用户授权。
- 失败时如何避免留下脏数据。

默认不写真实数据库、不删除真实对象、不重放真实支付或订单。任何例外都需要用户明确授权。

## 结果表达

使用以下措辞区分事实：

- “代码已实现，尚未部署验证”。
- “单元测试通过，跨系统字段尚未核对”。
- “E2E 失败，原因为数据依赖，不判定为代码缺陷”。
- “环境阻塞，未能完成验证”。

不要将未执行、弱断言通过或仅有本地产物写成端到端完成。
