# ylk-tech-doc

正式中文工程文档的三阶段流水线：**markdown 起草 → 图表美化 → 制式 docx**。

适用于任何需要提交给第三方（测评机构、甲方、评审组、招投标）的成套技术文档。典型产物形态：

```
<主题名>/
├── <主题名> - 设计方案（mermaid）.md   # 起草版，图用 mermaid
├── <主题名> - 设计方案.md              # 插图版，图用 PNG
├── <主题名> - 验收方案（mermaid）.md
├── <主题名> - 验收方案.md
├── <主题名> - 设计方案.docx            # 制式终稿
├── <主题名> - 验收方案.docx
└── images/                            # 原始未压缩 PNG
```

命名统一为 `<主题名> - <文档类型>`（空格 + 短横 + 空格），目录名为纯 `<主题名>`，markdown 主标题（`#`）与文件名一致。

**若项目中已有同类成稿，先读一套作为样板**——制式以样板为准，本 skill 记录的是样板里看不出来的规则。

---

## 三阶段

| 阶段 | 产物 | 关键动作 |
|------|------|---------|
| ① 调研编纂 | `（mermaid）.md` | 需求解读 → 章节骨架 → 正文与表格；图先用 mermaid 占位 |
| ② 图表美化 | `.md` + `images/` | mermaid → PNG（复用既有插图 / 生图工具），正文逐字不变 |
| ③ 最终输出 | `.docx` | `scripts/md2docx.py` 以样板 docx 为模板生成 → `scripts/check_docx.py` 校验 |

两版 markdown **正文必须逐字一致**，差异仅在图形载体（mermaid 代码块 vs `![](images/…)`）。保留双版的意义：mermaid 版便于 diff 与协作修订，插图版用于生成 docx。

## ★ 默认响应约束（用户既定要求，产出即遵守，无需提醒）

以下八条是用户对成套文档的既定要求，**每次产出/修订/校对默认执行**，不是可选项：

1. **数据准确、内容完整、逻辑自洽、前后一致**。跨文档（设计方案↔验收方案）关键判据须逐项对齐（同一指标在两端数字、单位、口径完全一致）；删改一处后全文检索该概念是否还有残留引用（高发缺陷：删用例后正文仍引用其编号）。
2. **行文风格整体一致，编号不乱序**。表号图号连续无缺口；术语先定义再全文统一；数字格式（千分位、量级表述）全文同一；跨文档同一对象表述统一（如「性能场景请求成功率」）。
3. **章节设计合理，符合格式规范**。以**已过审的同类成套文档为样板**（格式规范的活标准），章节骨架、颗粒度、表格密度对齐样板；本套件其余已过审设计方案即对照基准。
4. **全文无修订痕迹、无 AI 生成痕迹**。除「参考资料」章外无外部引用；无 `alt text` 占位符、`--` 连字符残留、封面错字（如「标标」）、「详见申报书 x.x.x」类外部章节号引用、AI 痕迹词。封面信息块、注释块逐字核对。
5. **指标理解勘误先行**。立项/申报指标原文必须先做术语界定与口径勘误（如规则数≠执行次数≠区块高度），锁定权威口径后全文统一；被勘误的旧口径不得进入正式文档。
6. **可视化/界面呈现类功能在验收环节必须有对应用例承接**。仪表盘、KPI 展示等「用于验收环节」的功能不得在收敛时删到验收无用例——删除用例须同步检查正文中对它的引用，否则产生悬空引用（实证：删 T-19 可视化用例后 3.1.1 仍写「界面呈现的正确性由 T-17 独立验收」，T-17 已被改占）。
7. **围绕核心交付指标收敛**。设计方案与验收方案服务于「说服评审方按这套方法验证、核心指标能通过」，该详细的详细（容量核算、测量边界、口径论证），该简略的简略（无关功能不灌水）。
8. **准确、权威、符合通用行业实践**。容量/性能验收方法引用通行标准（GB/T 25000.51、ISO/IEC 25010 等）时，须说明其合理性且经得起追问；最终一致性、生产部署形态判据等业界通行口径要写明依据。
9. **交付终态修订记录只保留最终编撰一条**。终稿 docx 修订记录收敛为单行「{编撰人} 全文编撰 {日期}」，不保留「梳理优化」「校对」等过程性修订；封面签署栏「编制」与修订记录「更改人」同口径。详见阶段③「交付终态修订记录与签署栏」。

> 上述约束的落实动作见「收尾校对清单」。

## 阶段① 调研编纂

### 内容口径（决定文档成败，比格式重要得多）

这类文档的真实读者是**评审方**，目标是「说服对方按这套方法验证、且核心指标能通过」。据此：

- **锁定核心指标，克制伴生指标**。伴生指标（吞吐、并发、响应分位数之类）不要设得比核心指标更苛刻，那是自缚手脚；但也不能松到一眼看出注水。可采用业界通用做法（按标准抽样、分层核验、就高合并工况）降低执行难度，但**必须说明其合理性**，且合理性要经得起追问。
- **收放自如**。与核心指标直接相关的详写，无关功能不灌水；也不能省到晦涩难懂。颗粒度对齐同类成稿。
- **各司其职**：设计方案答「怎么设计达成」，验收方案答「怎么测、凭什么信」，测试报告答「实测结果如何」。三者不互相串味。
- **检验项要精简**。能合并的合并（就高原则）；被定性为「参考项」「可选项」的，先问是否可以直接删除——连同对应的用例、测试方法与技术设计一并删掉，而不是留着占篇幅。**但「用于验收环节」的功能（可视化/仪表盘/界面呈现核验）不属精简对象**——验收环节须有对应用例承接，删到悬空引用是缺陷。

### 禁写表述

| 禁写 | 原因 |
|------|------|
| 「合同强制」「必须达成」 | 内部压力话术，不应出现在对外文档 |
| 「超额满足」「超额目标」 | 申报/承诺口径即设计目标，不存在超额一说 |
| 「最小修订」「本次调整」 | 那是给执行者的工作要求，不是文档内容 |
| 「评审专家」「专家组」 | 有无专家、有无评审环境都属项目安排，文档内不点名 |
| 修订痕迹、AI 生成痕迹 | 终稿须自成体系 |
| 外部章节号引用（「详见申报书 5.3.4」） | 全文自洽，除「参考资料」章外不引外部；外部约束改写为文档内声明 |
| 内部改进文档引用（偏离表/整改建议书/终检报告） | 交付终态文档不引用内部改进指导文档；偏离/偏差表述按「问题全部解决后」的终态口径书写（实证：6 份功能方案第 7 章「系统性偏差」整章改写为「实现符合性评估」，矩阵偏差项全部改「达成」） |

> 通则：**给 AI 的工作指令不等于文档内容**。用户说「做最小修订」「重点说服评审」，这些是过程要求，不能原样写进正文。

### 章节骨架（按主题增删）

- 设计方案：引言 → 架构设计 → 容量/功能描述 → 性能设计 → 安全设计 → 软硬件配置要求
- 验收方案：引言 → 性能设计 → 验收测试方案（数据制备 / 功能验证 / 性能验证 / 判定准则）→ 测试结果与验证 → 软硬件配置要求

### 编号与术语

- **术语先定义再全文统一**。例如把「测试用例」与「检验项」分设为 `T-xx` 与 `R-xx`，就不得再混称「验收项」。两套编号应双向覆盖，收尾时用脚本验一遍无遗漏、无悬空引用。
- 表号图号 = `章号-章内序号`（如「表 3-7」「图 2-1」），表题图题一律放在**下方**。
- **拆分成多份文档时各自独立编号**，从 1-x 重起，不沿用拆分前的编号；同时复核所有交叉引用（这是拆分后最高发的缺陷）。

## 阶段② 图表美化

- **优先复用既有插图**。原始材料（甲方文档、既有设计稿）里的图，只要流程结构没变就直接用，比重画更可信。但要核对图中文字与当前口径是否冲突（如原图标注的量级已变）。
- 需要新图时用生图工具（如 `baizhi-image-generate`）。同一套文档风格必须统一，建议：**简约科技风、白底、美观大气**。
- **非时序 Mermaid 图必须完成美化闭环。** 架构图、部署图、网络拓扑图、流程图、状态图、数据制备图等，在插图版中不得直接使用 Mermaid 默认渲染 PNG；必须经百智云图生图或等效信息图重绘，统一为白底、简约科技风。重绘后须逐节点、逐连线、逐分支核对语义，再替换正式图片；插图版与 docx 只能引用已美化且已核验的 PNG。时序图因需精确表达参与者、消息顺序与测量边界，可保留 Mermaid 渲染。
- **建立图表资产映射，不得按任务返回顺序或临时文件名认领图片。** 每张图在美化前先记录「图号/图题 → Mermaid 源码块 → 目标文件名 → 必须保留的节点、连线和分支」；图生图任务完成后，必须以实际视觉内容逐张回填映射。生成结果可能出现任务顺序交叉、输出文件名与内容不符等情况，最终归档只能按语义匹配，不能按任务 ID、返回数组顺序或下载文件名推断。
- **采用两向核验。** 正向核验 Mermaid/章节描述中的节点、连线、分支在 PNG 中均存在且文字正确；反向核验 PNG 的实际内容确实符合该图号、图题和上下文语义。只有两向核验都通过，才允许覆盖 `images/` 正式文件。临时图应保留任务 ID 或 `.optimized` 后缀，完成映射前不得直接覆盖正式图。
- **不要手工像素级调图**。图不对就改提示词重新生成，或用图生图定点修改（prompt 写明「保持全部内容、文字、配色、布局、风格不变，只做一处修改：…」）。手工微调既慢，效果也差。
- 生图任务可能失败，重试即可。生成后**逐节点比对**，模型常多画或少画连线；图生图完成后要重新读取当前文件，不得沿用上一次任务或旧文件的视觉判断。
- `images/` 存**原始未压缩 PNG**。docx 嵌入时会被压缩（实测 30–56%），反哺 markdown 时不得从 docx 里抠图。

## 阶段③ 最终输出（docx）

### 生成

```bash
python3 scripts/md2docx.py [--spec spec.json] \
    <样板.docx> <源.md> <输出.docx> <封面行1> <封面行2> <文档标题>
```

**封面标题两行规范**（0512 项目定稿口径，用户 2026-08-24 确认）：

- 行 1 = `<指标名>指标`（如 `数据加密传输成功率指标`）——**不带「0512项目」前缀**（2026-08-24 用户指示去除，项目信息由编号与封面元信息承载）
- 行 2 = 文档类型（`设计方案` / `验收方案` / `实现方案` / `测试报告`）
- 行 1 不得写成公司名/平台名（如「广州医药研究研究港口有限公司」「数据要素流通平台项目」——曾整批出错），也**不要带「指标」后缀时又叠写文档类型**（如「0512项目XX指标 设计方案」拼在一行）
- 成品交付目录文件名 = `{项目代号}-{指标序号两位}-{类型码}{类内序列两位} <行1><行2>.docx`（如 `0512-03-D03 数据加密传输成功率指标 设计方案.docx`（「指标」与文档类型之间用空格分隔，**文件名不带「0512项目」**，项目信息已在编号中）
- 类型码：**D**=设计方案（Design）、**R**=实现方案（Realization）、**T**=验收方案（Test）。字母序 D<R<T 恰好对应 设计→实现→验收 的文档语义流，同指标三份按文件名排序自然成组有序；各类型序列独立编号（D01-D06、R01-R07、T01-T06）；不用 I（Implementation）做实现方案码——I 与数字 1 视觉混淆
- **R 类（功能指标/技术方案）命名用功能项主体名 + 「 技术方案」**：D/T 类按指标粒度一份（文件名 = 指标名 + 空格 + 文档类型，如 `0512-03-D03 数据加密传输成功率指标 设计方案.docx`）；R 类按功能项拆分（如指标 03 拆「国密加密传输」「数字身份认证」两份），文件名 = `{编号} {主体名} 技术方案.docx`。一个指标拆多份 R 类时用指标名会同名冲突（实证：指标 03 两份曾完全同名）。**「功能」后缀不是通配规则**：主体名本身语义完整时不再追加（实证：R06「基于智能合约的跨域数据使用控制」加了「功能」反成病句，已去除；R03「国密加密传输」需加「功能」才是名词短语）。封面行 1 同理——「0512项目{主体名}」在主体名完整时不加「功能」
- md 头部注释元信息块须含 `交付文件：final/<最终文件名>.docx` 关联行，且 `项目名称` 与行 1 逐字一致

以**同类样板 docx 为模板**：保留其封面、签署栏、修订记录、页眉页脚与样式集，清空目录之后的正文，按 md 重建。样板选最近定稿的一套（制式最新）。

输入必须是**阶段②的插图版 md**。误传 mermaid 版会丢掉全部图（脚本跳过 mermaid 块，只在 stderr 留一行告警，终稿看不出来）。

层级约定：`#` 是文档标题、`##` 是章、`###` 是节。源 md 若用 `#` 作章标题，脚本会直接报错要求先调层级——不会静默丢弃。`#####` 及更深层级压到三级标题呈现，不进目录。

对模板的前提：封面标题行是 body 顶部的普通段落（不在表格里）、标题行不含冒号、日期栏以「项目时间」开头、标题样式挂了 Word 自动编号。任一不满足脚本会告警，但不会中断——按告警人工补。

项目中若无样板，需先手工制作一份合格 docx 作为模板（封面、签署页、目录、正文四段分节齐备），后续全部由脚本套用。

列表支持任意层级嵌套与有序列表，缩进步长（2 空格 / 4 空格）自动识别。项目符号与序号是手工写进文本的，不用 Word 自动编号列表——后者会吞掉行首前缀，且样式随模板漂移。

### 换制式（换模板必读）

表宽、底纹、目录字体字号、代码字体、封面日期栏键名等制式常量集中在 `scripts/_docx_spec.py` 的 `DEFAULT_SPEC`，**生成侧与校验侧共用同一份**。换模板时写个 JSON 只列要改的键：

```json
{"tbl_width_dxa": 9072, "header_fill": "D9D9D9", "toc_sz": "21"}
```

生成与校验都传同一个 `--spec`，否则会出现「生成的文档永远校验不过」且报错不指向根因。

### 校验

```bash
python3 scripts/check_docx.py <文档.docx> [对应的.md] \
    [--tmpl-tables N] [--sections N] [--spec spec.json]
```

覆盖 11 项：分节点、章分页、域配对、书签引用与落位、dirty 域、目录字号、表格版式、表格数/图片数与 md 对账、目录↔正文一致性。脚本生成的文档应当全绿。不适用的项（无目录、无表格）标 `[--]`，不计入结论。

- `--tmpl-tables N`：模板自带表格数（签署栏、修订记录等），默认 2，这些表不参与正文版式校验。
- `--sections N`：期望分节数，默认 3（四段分节）。模板制式不同时调整。
- **`check_docx.py` 全绿不等于图文语义正确。** 生成 docx 后，必须解析 `word/document.xml` 与 `word/_rels/document.xml.rels`，建立「图题/上下文 → r:embed → word/media 文件」映射，并将嵌入媒体与 `images/` 正式 PNG 做 MD5 对账；随后按图题逐张目视确认内嵌图片内容未错位、未互换。

改动脚本后跑 `scripts/selftest.sh <模板1.docx> [模板2.docx]` 回归——传两份结构不同的模板才能验出通用性退化。

> 手工维护的早期文档常在「章分页 / 表宽 / 目录字号 / dirty 域」报 `!!`，多为历史差异而非脚本误报，需人工判定是否回改。

### 制式要点

四段分节：**封面 → [分节] → 签署页+修订记录 → [分节] → 目录 → [分节] → 正文**，正文页码重新起编，每章一级标题另起页（首章紧随文档标题，不另起）。

| 项 | 值 |
|----|-----|
| 页面 | A4 11906×16838，上下边距 1440，左右 1797，docGrid linePitch 326 |
| 表格 | 定宽 8856 dxa 居中、全边框 sz=4、首行 `tblHeader` 跨页重复 + 底纹 `BEBEBE` + 加粗居中；数据行左对齐不加粗 |
| 目录 | `TOC \o "1-2" \h \u`，条目为 `HYPERLINK \l _TocXXXX` 域包裹「标题 + 点线制表位@8640 + `PAGEREF \h` 页码域」，宋体小四（sz=24） |
| 图片 | 最大宽 6 英寸，段落样式 Body Text、缩进清零、居中 |
| 正文对齐 | 左对齐（Normal 样式 `w:jc=left`，不用两侧对齐 both） |
| 代码块 | 仿宋、字号 22（正文 24 小一号）、浅灰 #595959，与正文黑色区分 |

完整 OOXML 细节见 [`references/docx-format.md`](references/docx-format.md)。

**交付终态修订记录与签署栏**（用户 2026-08-25 定稿，实证：0512 功能方案 12 份 docx 收敛）：

- 交付给第三方的终态 docx，修订记录表只保留**一行**：`1 | A/0 | {发布日期} | 全文编撰 | {更改日期} | {编撰人}`。不保留「梳理优化」「校对」「修订」等过程性条目——那是内部工作痕迹，不应出现在交付终稿。
- 日期沿用模板既有格式（如 `2026/8/21`，不带前导零），不另造格式。
- 封面签署栏「编制」与修订记录「更改人」同口径：编制人即全文编撰人；删除早期模板遗留的其他署名（实证：「编制：孟天伦 顾小宇」→「编制：顾小宇」）。
- 收敛后验证：zip 可正常解压、去标签后全文无旧署名/过程性修订词残留。

**SQL 与配置代码块在 docx 里不能用编号列表（numPr）**——实测 Word 编号列表会吞掉行首的 `ur.`、`id` 等前缀文本。脚本已按等宽段落（Consolas）逐行渲染。

生成 docx 必须以**插图版** md 为输入。若误传 mermaid 版，脚本会跳过 mermaid 块并告警——图形会缺失，需换用插图版重新生成。

## 目录页码：必须知道的事实 ★

**页码不是脚本能算出来的，也不该去估算。**

成稿目录里的真实页码，是**人用 Word/WPS 打开保存后**才写进文件的（查 `docProps/app.xml` 的 `Application` 字段即可确认文档最后由谁排版）。生成脚本写入的一律是占位值 `1`。

所以脚本的职责只有一个：**把域结构做对，让 Word/WPS 打开时自己算**。做法是给所有域的 `w:fldChar begin` 加 `w:dirty="true"`，配合 `settings.xml` 的 `updateFields` —— 打开即重算，无需手动 F9。

交付前用 Word/WPS 打开一次，确认页码正确并保存，真实值即固化进文件。

> 走过的弯路：曾试图用页面几何自建版面估算器，再拿已定稿文档做系数拟合来「训练」页码。这是错的——页码是排版引擎的确定性输出，不是待拟合的统计量。遇到「结果本该确定却算不出」时，正确反应是检查产出链路哪一环没执行，而不是去建模逼近。

## docx 直改技术要点（XML 层后处理）

需要直接改 docx 正文结构（修订记录收敛、签署栏署名、残留词清理等），不必重跑 md2docx 时：

- docx 是 zip，正文在 `word/document.xml`。用 `zipfile` 读该 item → 字符串替换 → 重写 zip（**其余 item 保留原始字节**）→ `os.replace`。改前先备份到 /tmp。
- **跨单元格的正则必然不命中**：表格相邻单元格文本（如「编  制」与署名「孟天伦 顾小宇」）中间隔着 `</w:tc><w:tc>` 标签，形如「编...孟天伦」的跨标签正则永远匹配不上。必须先 `re.sub(r'<w:tbl>.*?</w:tbl>', handler, xml, flags=re.S)` 定位含关键字的整表，再在表内替换 `<w:t>` 文本或删 `<w:tr>`。
- 删行 = 删 `<w:tr>` 整段（保留含 `<w:tblHeader/>` 的表头行）；改单元格文本 = 替换 `<w:t>…</w:t>` 内容（`w:t` 可能带 `xml:space` 等属性，整段文本替换直接用原样 `<w:t>` 标签）。
- 验证：`zipfile.testzip()` 确认可解压；去标签后全文断言目标词存在、旧署名/过程性词无残留。
