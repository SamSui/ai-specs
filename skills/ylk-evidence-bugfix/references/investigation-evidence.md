# Bug 调查与证据链

> 来源与时效性：见 [来源与时效性](sources-and-freshness.md)。接口、数据库、日志与部署结论必须在目标环境重新验证，不能由本文件或历史样例推断。
>
> **读取时机**：收到新 Bug 后，在修改代码前读取；涉及远程环境、数据库、日志或文件时按对应章节取证。**不能替代**：当前仓源码、CI 配置、实际 API 响应、数据库 schema 或运行时资源。

## 调查步骤

### 1. 静态链路

从前端请求定义开始，查：路由、API 封装、Controller mapping、Service、Mapper/Repository、Feign/RPC、下游 Controller、下游落库和回读 API。

常用命令：

```bash
rg -n "<route>|<api-method>|<field-name>" <frontend> <backend>
rg -n '@RequestMapping|@GetMapping|@PostMapping' <backend>/src
rg -n '<service-method>|<feign-method>|<mapper-method>' <backend>/src
```

输出每一跳的文件、方法、字段名、输入和输出。遇到多个分支时必须说明命中条件。

### 2. API 证据

- 先检查 API 的准确 HTTP 方法和路径；405/404 不可解释为业务故障。
- 保存脱敏请求、HTTP 状态和关键响应字段。
- 用户直接提供完整可执行的只读 curl 时，它是不可变原始证据：必须直接逐字节原样执行，不得手工重写 Token、删除 Header、替换 Cookie、添加管道或改变请求体。执行输入与脱敏报告严格分离，脱敏模板不得反向生成执行命令；若因工具限制必须转录，先对原文与待执行文本做字节级校验，任何字符、Header、Cookie、Referer、请求体、参数、引号或换行差异均停止，不执行修改版。执行时禁止 `set -x`、`curl -v` 等会泄露请求内容的输出方式；原始 stdout/stderr 不得回显或持久化，只能从其生成脱敏摘要。
- 凭据边界：不得回显、长期落盘或传播凭据，不等于不得使用用户明确提供的完整只读请求取证。用户提供的请求凭据仅可用于该次执行进程或受控临时载体；临时载体权限必须为 `0600`、限定本次执行生命周期且用后立即删除，不得写入 shell 历史、日志、文档、Beads、Git 或子 Agent 提示词。无法同时满足原样执行和隔离要求时停止；报告只写认证是否使用及脱敏失败类型。
- curl 失败时先记录不含凭据的退出码、传输错误或 HTTP 状态和脱敏响应摘要，并分类为传输、认证、方法/路由、服务端或业务错误。单次失败不得推断 Token 是根因，也不得修改原始请求；远程探针失败只阻断该探针，不阻断代码、CI、部署映射等静态调查，除非缺失的远程证据会改变修复决策。
- 对比至少一个正常样例和一个异常样例时，使用相同接口、同一环境、同一字段集。

### 3. 日志证据

先定位实际 deployment/namespace/selector，再查日志：

```bash
kubectl get deploy -A | rg '<keyword>'
kubectl get deploy <deploy> -n <ns> -o jsonpath='{.spec.selector.matchLabels}'; echo
kubectl logs -n <ns> deploy/<deploy> --tail=300 | rg '<request-id>|<business-id>|ERROR|Exception'
```

日志结论必须与请求时间、业务主键、运行版本对应。无相关日志不能推导“服务没有收到请求”。

### 4. 数据库证据

先确认环境、数据库、表、主键和列，再执行只读查询：

```sql
SELECT <id>, <state>, <relevant_columns>
FROM <table>
WHERE <business_key> = ?;
```

必须区分：

- 正常列、JSON 列和 transient 字段；
- 主表、记录表、缓存表和异步回写表；
- 路径、Base64 内容、物理文件名、业务展示名；
- 当前数据与历史数据。

不要将不存在列的 SQL 报错解释为“字段为空”。先用 `DESC <table>`、信息 schema 或 Mapper/实体定义确认 schema。

### 5. 对象存储证据

涉及文件或对象时，按实际链路选择并核对：

```text
输入路径、对象 key 或内容
→ 编码或传输形式（如适用）
→ 文件名或展示元数据（如适用）
→ 上传、复制或生成结果（如适用）
→ 数据库存储或引用（如适用）
→ 下游接口
→ UI 展示、下载或消费行为（如适用）
```

使用对象存储时，单独验证对应 SDK 或存储系统的返回值、异常吞吐和错误 fallback；不得默认使用 MinIO、Base64、数据库列或 UI。

**路径类型与集合协议门禁：** 仅当输入可能表示目录、前缀、数组、逗号分隔值或多个对象时，确认其实际类型和集合边界。本地路径执行 `test -f` 或 `test -d`；对象存储通过对象列表或元数据确认单对象、前缀集合或归档对象。证据表至少记录 `输入值、类型、对象数量、传输标识、展示标识、验证命令和结果`。存在集合语义时，必须穷举完整数据集合，并记录枚举命令、递归范围、分页或截断状态、返回总数和结束条件；不能证明集合完整时，不得制定选择、排序、丢弃或转换方案。集合完整后，确认发送方编码方式、传输字段语义、下游接收类型、解包/遍历规则、顺序是否有业务含义，以及空集合和单项兼容行为。单对象路径仅验证对象存在性、类型、传输和错误处理。任何数据选择必须引用协议或代码证据并说明其余数据的处理结果。

新字段通常遵循既有同类字段机制；若发现共享历史问题，不能未经范围确认扩散修复。

## 证据状态与计划失效

维护下列证据状态，防止新证据被旧方案覆盖：

| 状态 | 含义与处理 |
|------|------------|
| 已确认事实 | 由代码、API、对象元数据、数据库或日志直接证明；不得在后续计划中降级为假设或删除。 |
| 待验证假设 | 明确标出证据缺口，不得据此实施或推出文件选择、协议或部署结论。 |
| 已排除假设 | 记录反证及其适用条件。 |

新增证据若改变输入、对象类型、协议语义、根因、影响范围或部署模型，原计划立即标记为 `STALE`，停止实施；更新证据表、根因、假设、范围与验证项后，重新进行独立计划审查。只有更新且可复核的矛盾证据可以改变已确认事实，且必须同时保留旧证据、新证据和影响说明。

## 常见误区

1. 只看 DTO、VO 或前端模板，未确认实际查询分支。
2. 将远端响应当作唯一数据源，忽略本地镜像/缓存优先的详情分支。
3. 把 `@TableField(exist = false)` 当作数据库列。
4. 对 JSON 对象无条件 `new` 后整体覆盖，清空响应中未包含的历史字段。
5. 使用 `isEmpty` 时忽略纯空白字符串；字段语义需要“无有效内容”时用 `isBlank`。
6. 未验证工作目录，在错误 Maven reactor 或错误前端项目执行测试。
7. 将全量构建的仓库既有失败归因于本次改动。
