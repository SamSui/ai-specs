# 项目认知、经验与 Beads memory

## 目的

`CURRENT_TASKS.md` 和 `CURRENT_E2E.md` 的长期价值不只在任务跟踪，还在于它们保存了项目认知、调查经验、验证方法和踩坑记录。引入 Beads 后，这些内容不能丢失，而应按稳定性分流到 Beads issue、Beads memory、ADR 和结果报告。

## 四类内容的承载规则

- **任务进展** → Beads issue；状态、负责人、依赖、待办、当前阻塞和验证轮次。
- **项目认知** → Beads memory；仓库拓扑、服务职责、跨仓关系、环境矩阵、字段语义和长期事实；设计阶段即可写入，但必须有事实依据。
- **经验与踩坑** → Beads memory；可重复失败原因、错误判断、验证陷阱、构建/部署/测试经验；原则上在获得实施授权并进入实施阶段后记录。
- **稳定架构决策** → ADR + Beads memory；ADR 是正式来源，memory 便于后续任务快速召回。
- **本轮最终结论** → ADR / `result.md` / `HANDOVER.md`；有证据的阶段性结论、验证汇总和剩余风险。
- **一次性过程日志** → Beads notes 或历史文件；除非提炼出可复用规则，不进入长期 memory。

## 什么时候写 Beads memory

设计阶段可以写入或更新已核实的项目认知；实施阶段可以进一步写入实施中确认的经验、规则和踩坑。满足任一条件就考虑写入或更新 memory；其中项目认知可在设计阶段记录，经验和踩坑原则上在实施阶段记录：

- 下一次跨仓任务如果不知道它，会重复调查或容易改错。
- 用户明确确认了一个后续必须遵守的规则。
- 发现名称与实际行为不一致、字段来源容易误判或跨系统契约容易破坏。
- 同类构建、测试、E2E、微前端或部署问题可能再次出现。
- 项目认知跨越多个仓库，无法自然归属于某一个仓库的 README。

写入前检查：

- 搜索 `bd memories <keyword>`，优先更新已有 key。
- 确认事实来源于代码、ADR、测试、环境或用户确认。
- 写清适用范围和后续应用方式。
- 去除敏感信息和一次性状态。

## 不写入 memory

- 当前 issue 尚未确认的假设、方案偏好或未经证实的设计推断。
- 单次命令输出、单轮进度和已解决的临时阻塞。
- 代码和 CLAUDE.md 已清楚记录、无需额外解释的事实。
- 凭据、Token、密码、私钥、完整连接串、Cookie、Authorization header、敏感 IP、用户身份证号或生产数据。
- 为了恢复上下文而复制完整日志或未经脱敏的 API 响应。

## memory 格式

优先使用有意义的稳定 key，并在内容中写清事实、适用范围和应用方式：

```bash
bd remember --key ylk-<topic> "
事实：<已经核实的规则或坑>。
适用范围：<仓库、模块、场景>。
如何应用：<后续任务开始前应做什么>。
来源：<ADR 路径或验证类型>。
关联：<其他 memory key/ADR>。
"
```

更新已有内容而不是重复创建：

```bash
bd memories <keyword>
bd remember --key <existing-key> "更新后的完整内容"
```

## 记忆类别示例

### 项目认知

适合记录：

- `datafield-workbench`、`datafield-bridge`、`datafield-platform` 及对应前端之间的职责和数据流。
- 某个结果表、订单、资源、对象存储或路由元数据的跨仓所有权。
- 已确认的环境组合、命名契约、生命周期和字段单一来源。

### 经验

适合记录：

- Maven Wrapper、JDK 版本、模块入口、Surefire 或增量编译的可重复约束。
- 微前端/Wujie/SPA 的真实导航方式和常见错误。
- 跨系统验证必须比较哪些字段，哪些 API-only 结论不充分。
- 前端 ZIP 包裹目录、部署目录、rollout 和静态资源缓存的常见陷阱。

### 踩坑

设计阶段不要把方案假设或未验证推断记录为踩坑。获得明确实施指令并进入实施阶段后，确认了可复现失败原因时，每条踩坑尽量写成以下结构：

```text
症状：看到什么错误或假通过。
根因：经过代码/环境/数据证据确认的原因。
错误做法：为什么之前的判断或命令不可靠。
正确做法：下次先检查什么、使用什么命令或路径。
影响范围：哪些仓库、模块或场景适用。
关联：ADR、Beads issue、相关 memory key。
```

### 用户决策

用户确认的内容必须和推测区分，尤其是：

- 不迁移旧数据或不保留 fallback。
- 环境矩阵只有哪些合法组合。
- 哪些仓库属于本轮，哪些仓库明确不改。
- 外部动作需要什么授权。

## 每轮收官动作

任务结束前：

1. 从父 issue 和子 issue 中筛出新出现的稳定认知、经验和踩坑。
2. 搜索 `bd memories <keyword>`，更新已有 memory，避免重复。
3. 将正式架构决策写入 ADR，并在 memory 中保留便于召回的摘要（确有必要时）。
4. 将本轮状态、失败和未完成项留在 issue/result，不污染长期 memory。
5. 不把未验证推断或敏感环境数据写入 memory。
