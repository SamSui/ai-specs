## 2. 测试用例要素规范

### 2.1 必需要素 (12 项)

每个测试用例**必须**包含以下 12 个要素：

| 序号 | 要素名称 | 说明 | 示例 |
|------|---------|------|------|
| 1 | **用例编号** | 唯一标识符 | TC-001 / TC-R03-007 |
| 2 | **用例标题** | 简洁描述测试目标 | PostgreSQL 标准接入 |
| 3 | **优先级** | P0/P1/P2 | P0 (最高) / P1 (中) / P2 (低) |
| 4 | **测试类型** | 功能/边界/性能/容错等 | 功能测试 / 边界测试 / 性能测试 |
| 5 | **对应需求** | 追溯到具体需求模块 | 1.1 数据库接入 |
| 6 | **对应用收标准** | 追溯到验收标准条款 | 3.1.4-1 |
| 7 | **用例描述** | 详细测试目标和范围 | 验证系统能够... |
| 8 | **测试数据** | 具体数据规格和准备要求 | PostgreSQL 12+, 100 行表 |
| 9 | **预置条件** | 执行前必须满足的条件 | 数据库服务已启动并可访问 |
| 10 | **测试步骤** | 详细操作步骤 (编号列表) | 1. 配置... 2. 启动... 3. 检查... |
| 11 | **预期结果** | 明确的可验证结果 | ✅ 连接成功，无报错... |
| 12 | **通过标准** | 量化的判定标准 | 100 条记录全部成功导入，数据准确性 ≥ 95% |

### 2.2 可选要素 (推荐)

以下要素根据测试类型选择性添加：

| 要素名称 | 适用场景 | 说明 |
|---------|---------|------|
| **性能指标** | 性能测试 | 处理时间、内存占用、吞吐量等 |
| **失败标准** | 边界/容错测试 | 明确判定失败的条件 |
| **注意事项** | 复杂测试 | 环境要求、风险提示等 |
| **指标记录** | 需要量化统计的测试 | 预留数据记录位置 |
| **边界条件** | 边界测试 | 说明测试的边界值 |
| **降级说明** | MVP 降级验证 | 说明降级接受的场景 |

### 2.3 要素编写要求

#### 2.3.1 用例编号规范

```
格式：TC-[模块前缀]-[序号]

示例:
- TC-001 (通用测试)
- TC-R03-007 (需求 3 的第 7 条)
- TC-BOUNDARY-001 (边界测试)
- TC-US-001 (用户故事场景)
```

#### 2.3.2 优先级定义

| 优先级 | 定义 | 占比建议 |
|--------|------|---------|
| **P0** | 阻塞性测试，核心功能，必须通过 | 60-70% |
| **P1** | 重要测试，非阻塞，应该通过 | 20-30% |
| **P2** | 边缘场景测试，可以延迟 | 5-10% |

#### 2.3.3 测试步骤编写要求

```markdown
**测试步骤**:
1. [动作] + [对象] + [预期反馈]
2. 使用祈使句，清晰简洁
3. 每一步都是可执行的原子操作
4. 步骤数建议 3-7 步，不超过 10 步

✅ 正确示例:
1. 在系统中配置 PostgreSQL 连接参数 (host, port, database, user, password)
2. 选择数据库中的 `test_users` 表进行接入
3. 启动数据接入任务
4. 监控任务执行日志
5. 检查接入结果报告

❌ 错误示例:
1. 配置数据库然后启动任务检查结果 (一步包含多个动作)
```

#### 2.3.4 预期结果编写要求

```markdown
**预期结果**:
✅ 使用 ✅ 符号标记每个预期结果
✅ 结果必须是可观察、可验证的
✅ 量化指标必须明确数值和阈值
✅ 与通过标准保持一致

示例:
✅ 连接成功，无报错
✅ 100 条记录全部接入成功
✅ 数据完整性 ≥ 95% (字段值准确)
✅ 接入时间 < 30 秒
```

#### 2.3.5 通过标准编写要求

```markdown
**通过标准**:
- 必须量化，可测量
- 必须与预期结果对应
- 必须明确阈值

✅ 正确示例:
- 100 条记录全部成功导入
- 数据准确性 ≥ 95%
- 任务状态为"成功"

❌ 错误示例:
- 系统正常工作 (不可量化)
- 性能良好 (无明确阈值)
```

## 6. 最佳实践示例

### 6.1 完整测试用例示例

```markdown
#### TC-001: PostgreSQL 标准接入

**优先级**: P0  
**测试类型**: 功能测试  
**对应需求**: 1.1 数据库接入  
**对应用收标准**: 3.1.4-1

**用例描述**:  
验证系统能够成功连接 PostgreSQL 数据库并完整读取表数据。

**测试数据**:
- PostgreSQL 12+ 数据库实例
- 测试表 `test_users` 含 100 条记录
- 表结构：id, name, email, created_at, status

**预置条件**:
- 数据库服务已启动并可访问
- 测试数据已准备完成
- 网络连通性正常

**测试步骤**:
1. 在系统中配置 PostgreSQL 连接参数 (host, port, database, user, password)
2. 选择数据库中的 `test_users` 表进行接入
3. 启动数据接入任务
4. 监控任务执行日志
5. 检查接入结果报告

**预期结果**:
✅ 连接成功，无报错
✅ 100 条记录全部接入成功
✅ 数据完整性 ≥ 95% (字段值准确)
✅ 接入时间 < 30 秒

**通过标准**:
- 100 条记录全部成功导入
- 数据准确性 ≥ 95%
- 任务状态为"成功"

---
```

### 6.2 边界测试用例示例

```markdown
#### TC-BOUNDARY-001: 超大文件 (5GB+) 上传与处理

**优先级**: P0  
**测试类型**: 边界测试  
**对应需求**: 数据接入层、流式处理

**用例描述**:  
验证系统能否处理超出常规范围的超大文件 (5GB+)

**测试数据**:
- 5GB 纯文本文件 (单行，无换行)
- 8GB 纯文本文件 (多行，密更换行)
- 10GB 结构化数据 (JSON/CSV)

**预置条件**:
- 系统内存监控工具已启动
- 磁盘空间 ≥ 20GB
- 系统配置：最大文件限制已关闭/设为 20GB

**测试步骤**:
1. 准备 5GB 测试文件
2. 使用上传功能上传文件
3. 监控内存占用 (watch -n 1 'ps aux | grep python')
4. 监控处理时间 (计时)
5. 检查处理结果完整性 (MD5 校验)
6. 检查系统日志 (无 OOM、无崩溃)

**预期结果**:
✅ 文件上传成功
✅ 流式处理完成 (不 OOM)
✅ 内存峰值 < 1GB (MVP 可接受降级)
✅ 输出文件与源文件内容一致
✅ 系统不崩溃，可继续处理新任务

**通过标准**: 全部预期结果达成

**失败标准**: 任一预期结果未达成 (OOM、崩溃、数据损坏)

**注意事项**:
- 需要在独立环境测试，避免影响其他进程
- 使用 /usr/bin/time -v 监控内存峰值
- 考虑磁盘 I/O 瓶颈 (建议 SSD)

---
```
