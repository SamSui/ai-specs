# 用户故事编写规范

> **版本**: v1.0  
> **创建日期**: 2026-04-29  
> **适用范围**: 所有软件工程项目的敏捷开发团队

---

## 1. 标准格式

每个用户故事必须包含以下要素：

```markdown
**US-{NNN}**: {简短标题}

**作为** [用户角色]，**我需要** [功能描述]，**以便** [业务价值]

**角色**: {具体角色名称}
**优先级**: P0 / P1 / P2
**所属模块**: {模块名称}

**验收标准**:
- {可验证的条件 1}
- {可验证的条件 2}
- {可验证的条件 3}
```

---

## 2. 要素详解

### 2.1 ID 编号

- 格式：`US-{NNN}`（如 US-101）
- 按模块分段：US-1xx（模块一）、US-2xx（模块二）等
- 全局唯一，不可复用

### 2.2 用户角色

| 类型 | 示例 |
|------|------|
| 终端用户 | 数据治理工程师、业务用户、系统管理员 |
| 技术用户 | 算法工程师、开发工程师、运维工程师 |
| 外部用户 | API 消费者、第三方集成方 |

**要求**：角色必须具体，避免使用"用户"这种模糊角色。

### 2.3 功能描述

- 使用动词开头（支持/可以/能够...）
- 描述"做什么"而非"怎么做"
- 不超过 30 字

### 2.4 业务价值

- 说明"为什么需要这个功能"
- 与业务目标直接关联
- 帮助团队理解优先级依据

### 2.5 验收标准

每条验收标准必须满足 **SMART** 原则：

| 原则 | 说明 | 示例 |
|------|------|------|
| **S**pecific | 具体明确 | ✅ "支持 CSV/Excel/JSON 文件接入" |
| **M**easurable | 可量化 | ✅ "100 个不同格式文件 100% 正确识别" |
| **A**chievable | 可实现 | ✅ "10 万记录处理<10 秒" |
| **R**elevant | 与需求相关 | ✅ "检测准确率≥95%" |
| **T**estable | 可测试验证 | ✅ "错误处理完整，50 个异常文件 100% 记录到 error.log" |

---

## 3. 优先级定义

| 优先级 | 含义 | 占比建议 |
|--------|------|----------|
| **P0** | MVP 核心功能，缺失则产品不可用 | ≤ 40% |
| **P1** | 重要功能，缺失影响用户体验 | ≤ 40% |
| **P2** | 优化功能，可做可不做 | ≤ 20% |

---

## 4. 用户故事与下游文档的映射

```
用户故事 (US-XXX)
    ├── 验收标准 → 验收标准文档 (AC-XXX)
    ├── 测试验证 → 测试用例 (TC-XXX)
    ├── 技术实现 → 任务卡片 (T-XXX)
    └── 架构影响 → ADR (如需要)
```

---

## 5. 反模式

| 反模式 | ❌ 错误示例 | ✅ 正确示例 |
|--------|-----------|-----------|
| 技术实现混入 | "使用 Redis 缓存用户会话" | "作为用户，我需要快速登录，以便提升使用体验" |
| 验收标准模糊 | "系统性能良好" | "1000 个文件扫描时间<1 秒" |
| 角色不明确 | "作为用户，我需要..." | "作为数据治理工程师，我需要..." |
| 缺少业务价值 | "支持文件上传功能" | "支持文件上传，以便接入多源数据" |
| 过大颗粒度 | "完成整个数据治理模块" | "支持 CSV 文件格式识别与接入" |

---

## 6. 检查清单

- [ ] 故事格式完整（ID/标题/角色/价值/优先级/模块）
- [ ] 角色具体可识别
- [ ] 验收标准≥3 条且每条可量化验证
- [ ] 与需求规格文档对齐
- [ ] 与测试用例已建立映射关系
