# 架构决策记录(ADR)编写规范

> **版本**: v1.0  
> **创建日期**: 2026-04-29  
> **适用范围**: 所有软件工程项目  
> **说明**: ADR 是记录项目关键架构决策的标准格式，确保决策过程可追溯、可理解。

---

## 1. 何时编写 ADR

以下情况必须编写 ADR：

- 技术栈选型（框架、数据库、消息队列等）
- 架构模式选择（单体/微服务/模块化单体等）
- 接口协议决策（REST/gRPC/GraphQL 等）
- 数据存储策略（关系型/文档型/缓存策略等）
- 安全认证方案（JWT/Session/OAuth2 等）
- 部署策略（容器化/Serverless/裸机等）
- 任何影响 2 个以上模块或团队的技术决策

---

## 2. 文件命名规范

```
decisions/
├── ADR-{NNN}-{short-description}.md
├── ADR-INVENTORY-{Milestone}.md      # ADR 索引清单
└── README.md                          # 决策目录说明
```

**规则**：
- 编号连续，从 001 开始
- `short-description` 使用小写 kebab-case
- 已废弃的 ADR 保留原文件名，在文档中标注 `SUPERSEDED`

---

## 3. ADR 标准格式

```markdown
# ADR-{NNN}: {决策标题}

## 状态

{提议 / 已接受 / 已废弃 / 已替代 by ADR-XXX}

## 日期

YYYY-MM-DD

## 上下文 (Context)

{描述决策前的背景、面临的问题、约束条件。说明"为什么需要做这个决策"。}

## 决策 (Decision)

{明确陈述做出的决策。使用"我们将..."的句式。}

## 备选方案 (Alternatives Considered)

### 方案 A: {名称}
- **优点**: ...
- **缺点**: ...

### 方案 B: {名称}
- **优点**: ...
- **缺点**: ...

## 后果 (Consequences)

### 积极影响
- ...

### 消极影响 / 风险
- ...

### 需要后续跟进
- ...
```

---

## 4. 状态流转

```
提议(Proposed) → 已接受(Accepted)
                      ↓
              已废弃(Deprecated) ←—— 被 ADR-XXX 替代(Superseded)
```

| 状态 | 含义 | 可修改内容 |
|------|------|-----------|
| **提议** | 正在讨论中，尚未最终确定 | 任何内容 |
| **已接受** | 团队达成一致，开始执行 | 仅可补充后果和跟进项 |
| **已废弃** | 决策不再适用，但有历史价值 | 仅更新状态 |
| **已替代** | 被新的 ADR 取代，旧决策失效 | 仅更新状态，指向新 ADR |

---

## 5. 检查清单

编写完成后自检：

- [ ] 编号连续，无跳跃
- [ ] 上下文充分说明"为什么需要决策"
- [ ] 至少对比了 2 个备选方案
- [ ] 后果包含积极和消极两方面
- [ ] 消极影响有对应的缓解措施或风险接受说明
- [ ] 与现有 ADR 无矛盾（如有，需引用并说明关系）
